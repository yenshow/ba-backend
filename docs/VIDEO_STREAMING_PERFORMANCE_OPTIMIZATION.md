# 視訊串流性能優化指南

## ⚠️ 重要建議

### **預設不使用 GPU 編碼（推薦）**

根據實際測試，**直接使用 MediaMTX 拉取 RTSP 串流效果更好**：
- ✅ **延遲更低**：1-2 秒（vs GPU 編碼的 7-8 秒）
- ✅ **畫面更流暢**：無卡頓
- ✅ **後端負擔更輕**：不需要額外的編碼處理
- ✅ **更簡單穩定**：減少一個處理環節

**建議**：除非有以下需求，否則**不要使用 GPU 編碼**：
1. 需要降低位元率（例如從 4M 降到 2M）
2. 需要轉換編碼格式（例如 H265 → H264）
3. 需要調整解析度（例如 4K → 1080p）

---

## 📊 當前問題分析

根據終端日誌和畫面延遲分析：

### 問題 1：編碼速度過慢（GPU 編碼）
- **現象**：FFmpeg 編碼速度只有 `0.3-0.7x`（應該接近 `1.0x`）
- **影響**：導致延遲累積，從 1-2 秒增加到 7-8 秒
- **原因**：
  - 解析度過高（2560x1440）導致編碼負擔重
  - 多餘的轉碼步驟增加延遲
  - 輸入源解碼錯誤（`corrupt decoded frame`）
- **解決方案**：
  - **最佳**：直接使用 MediaMTX（不勾選 GPU 編碼）
  - **次選**：如果必須使用 GPU 編碼，降低解析度到 1080p 或 720p

### 問題 2：畫面卡頓（GPU 編碼）
- **現象**：使用 GPU 編碼後畫面播放不流暢
- **影響**：用戶體驗差
- **原因**：
  - 編碼速度跟不上實時（0.3-0.7x）
  - 輸入源解碼錯誤導致重複幀（`dup=248`）
  - 多餘的轉碼步驟增加處理時間
- **解決方案**：
  - **最佳**：直接使用 MediaMTX（不勾選 GPU 編碼）
  - **次選**：降低解析度到 1080p 或 720p

### 問題 3：後端負擔（GPU 編碼）
- **現象**：編碼速度慢，GPU 使用率高，但效果不如直接使用 MediaMTX
- **影響**：系統資源消耗大，但性能反而更差
- **原因**：
  - 高解析度編碼負擔重（2560x1440）
  - 多餘的轉碼步驟（攝像頭 → FFmpeg → MediaMTX → HLS）
  - 輸入源解碼錯誤需要額外處理
- **解決方案**：
  - **最佳**：直接使用 MediaMTX（不勾選 GPU 編碼），讓 MediaMTX 直接拉取 RTSP
  - **次選**：如果必須使用 GPU 編碼，降低解析度到 1080p 或 720p

## ✅ 已實施的優化措施

### 1. 編碼參數優化

#### Preset 優化
- **修改前**：`p4: "fast"`（預設）
- **修改後**：`p4: "llhp"`（低延遲高性能）
- **效果**：提升編碼速度，降低延遲

#### 編碼模式優化
- **修改前**：`-rc vbr`（可變位元率）
- **修改後**：`-rc cbr`（固定位元率）
- **效果**：更穩定，低延遲

#### GOP 優化
- **修改前**：`-g 60`（2 秒關鍵幀間隔）
- **修改後**：`-g 30`（1 秒關鍵幀間隔）
- **效果**：減少緩衝延遲

#### 其他優化
- 禁用 B-frames：`-bf 0`（減少延遲）
- 低延遲調優：`-tune ll`
- 低延遲輸出：`-fflags +nobuffer+flush_packets`

### 2. MediaMTX 配置優化

已配置低延遲 HLS（LL-HLS）：
- `hlsSegmentDuration: 1s`（1 秒片段）
- `hlsPartDuration: 200ms`（200ms 部分片段）
- `hlsSegmentCount: 7`（保留 7 個片段）
- `writeQueueSize: 256`（減少緩衝）

## 🚀 進一步優化建議

### ⚠️ 方案 0：直接使用 MediaMTX（最推薦）

**根據實際測試，這是效果最好的方案**：

**優點**：
- ✅ **延遲最低**：1-2 秒（vs GPU 編碼的 7-8 秒）
- ✅ **畫面最流暢**：無卡頓
- ✅ **後端負擔最輕**：不需要額外的編碼處理
- ✅ **最簡單穩定**：減少一個處理環節

**實施方式**：
在前端**不勾選「啟用 GPU 編碼」選項**，讓 MediaMTX 直接拉取 RTSP 串流。

**適用場景**：
- ✅ 攝像頭已經輸出 H.264（大多數情況）
- ✅ 不需要降低位元率
- ✅ 不需要轉換編碼格式
- ✅ **優先考慮低延遲和流暢度**

---

### 方案 A：降低解析度（僅在必須使用 GPU 編碼時）

**優點**：
- 大幅降低編碼負擔
- 提升編碼速度
- 減少網路帶寬需求
- 降低延遲

**實施方式**：
在 FFmpeg 編碼參數中添加縮放過濾器：

```javascript
// 在 buildNvencArgs 中添加
args.push(
  "-vf", "scale=1920:1080", // 縮放到 1080p
  // 或
  "-vf", "scale=1280:720",  // 縮放到 720p（更低延遲）
);
```

**建議解析度**：
- **1080p (1920x1080)**：平衡品質和性能
- **720p (1280x720)**：最低延遲，適合監控

### 方案 B：降低位元率

**優點**：
- 減少編碼負擔
- 降低網路帶寬
- 提升編碼速度

**實施方式**：
修改預設位元率：

```javascript
// 在 DEFAULT_CONFIG 中
bitrate: "1M", // 從 2M 降到 1M
```

### 方案 C：使用 WebRTC（最低延遲）

**優點**：
- 延遲最低（< 1 秒）
- 不需要 HLS 分段
- 直接串流

**缺點**：
- 需要前端支援 WebRTC
- 配置較複雜

**實施方式**：
前端使用 WebRTC URL 而非 HLS URL。

## 🎯 最佳實踐建議

### 1. 根據需求選擇解析度

- **監控用途**：720p 或 1080p 足夠
- **高品質需求**：1080p 或 1440p
- **低延遲優先**：720p

### 2. 根據網路條件調整位元率

- **區域網路**：2M 或更高
- **網際網路**：1M 或更低
- **移動網路**：500K-1M

### 3. 監控並調整

- 定期檢查編碼速度
- 監控延遲變化
- 根據實際情況調整參數

---

## ⚠️ 注意事項

1. **降低解析度會影響畫質**：需要在品質和性能之間平衡
2. **降低位元率會影響畫質**：需要根據網路條件調整
3. **GOP 太小可能影響相容性**：30 是較安全的選擇
4. **CBR 可能導致畫質波動**：但對低延遲更有利
