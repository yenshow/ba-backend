## 系統概述

### 核心組件

1. **警報服務** (`alertService.js`) - 統一的警報創建、更新、查詢入口
2. **規則服務** (`alertRuleService.js`) - 規則查詢、評估、訊息格式化（含緩存機制）
3. **錯誤追蹤** (`errorTracker.js`) - 累積錯誤次數，觸發離線警報
4. **監控系統整合** - 環境監控（閾值警報）、照明監控（設備連線警報）
5. **清理服務** (`alertCleanupService.js`) - 自動備份和清理過期警報

### 警報狀態與類型

| 狀態       | 說明               | 行為                                          |
| ---------- | ------------------ | --------------------------------------------- |
| `active`   | 活動中的警報       | 可被更新、忽視、解決                          |
| `resolved` | 已解決的警報       | 可重新激活（unresolve），問題復發時創建新警報 |
| `ignored`  | 被管理員忽視的警報 | 不會創建新的同類型警報                        |

| 類型        | 說明         | 範例           |
| ----------- | ------------ | -------------- |
| `offline`   | 設備離線警報 | 設備連接失敗   |
| `error`     | 錯誤警報     | 系統錯誤       |
| `threshold` | 閾值警報     | PM2.5 超過閾值 |

### 嚴重程度

| 嚴重程度   | 數值順序 | 說明                         |
| ---------- | -------- | ---------------------------- |
| `warning`  | 1        | 需要關注，但尚未達到危險程度 |
| `error`    | 2        | 錯誤級別                     |
| `critical` | 3        | 需要立即處理的嚴重情況       |

## 警報規則系統

### 規則緩存機制

規則寫入資料庫後永久緩存，減少資料庫查詢約 20-30%。

- 首次查詢時從資料庫載入並緩存
- 後續查詢直接使用緩存
- 提供 `clearThresholdRulesCache()` 手動清除功能

### 已實現的規則（17 條）

| 系統來源      | 警報類型    | 規則數量 |
| ------------- | ----------- | -------- |
| `environment` | `threshold` | 14       |
| `device`      | `offline`   | 1        |
| `environment` | `offline`   | 1        |
| `lighting`    | `offline`   | 1        |
| **總計**      | -           | **17**   |

**環境系統閾值規則**：

- CO2：> 1000 ppm (warning), > 2000 ppm (critical)
- 溫度：≤ 20 或 ≥ 26°C (warning), < 18 或 > 28°C (critical)
- 濕度：≤ 30 或 ≥ 60% (warning), < 20 或 > 70% (critical)
- PM2.5：> 25 µg/m³ (warning), > 50 µg/m³ (critical)
- PM10：> 50 µg/m³ (warning), > 100 µg/m³ (critical)
- 噪音：> 55 dB (warning), > 70 dB (critical)

**離線規則**：連續 5 次錯誤 → `warning`

## 警報創建與更新流程

### 核心函數：`alertService.createAlert()`

#### 1. 前置檢查階段

- **忽視檢查**：優先檢查是否有被忽視的警報（閾值警報支持參數匹配）
- **現有警報查詢**：閾值警報需要參數匹配，其他警報使用標準匹配

#### 2. 更新或創建決策

**重要原則**：

- **同一天只會有一個 active 警報**（同一來源、類型、參數）✅ **已實現**
- 數值變化時必須更新 message
- Severity 根據數值範圍自動匹配規則
- **按天限制**：查詢現有警報時，只查詢當天（UTC）創建的 active 警報

**更新條件**：

- ✅ Message 變化（閾值警報）
- ✅ Severity 自動升級（根據數值範圍匹配規則）
- ❌ Severity 降級（不更新）
- ❌ Message 相同且 severity 相同（不更新）

**按天限制實現**：

- 使用 `getTodayDateRange()` 輔助函數獲取當天的開始和結束時間（UTC）
- 在查詢現有 active 警報時，添加 `created_at >= todayStart AND created_at < todayEnd` 條件
- 跨天後，即使問題相同，也會創建新的警報（符合文檔說明）

**Severity 自動更新範例**：

- PM2.5 = 30µg/m³ → 匹配 `> 25` → severity = `warning`
- PM2.5 = 60µg/m³ → 匹配 `> 50` → severity = `critical`（自動升級）

**按天限制範例**：

```
2025-01-06 10:18 → 創建警報（PM2.5 = 51µg/m³）
2025-01-06 15:30 → 更新警報（PM2.5 = 52µg/m³）← 同一個警報（同一天）
2025-01-07 10:18 → 創建新警報（PM2.5 = 53µg/m³）← 新警報（跨天）
```

## 忽視與解決處理

### 忽視功能

**忽視後的處理**：

- 不會創建新的 active 警報
- 忽視狀態保持不變
- 閾值警報：不同參數可以獨立被忽視（PM2.5 被忽視不影響 PM10）

**取消忽視**：警報狀態從 `ignored` 變為 `active`，問題仍然存在時會重新創建警報

### 自動解決

**閾值警報**：感測器數值恢復正常時自動解決  
**設備連線警報**：設備恢復連線、錯誤計數重置為 0 時自動解決

**已解決的警報**：

- 不會被自動更新（問題復發時會創建新的 active 警報）
- 可以通過 API 手動重新激活（`unresolve`）

## 設備連線警報 vs 閾值警報

### 核心差異

| 特性         | 設備連線警報                             | 閾值警報                                       |
| ------------ | ---------------------------------------- | ---------------------------------------------- |
| **觸發機制** | 錯誤計數達到閾值（連續 5 次失敗）        | 感測器數值超過閾值                             |
| **警報匹配** | 只匹配 `source + source_id + alert_type` | 額外匹配參數（PM2.5、PM10 等）                 |
| **更新邏輯** | 只更新 severity（severity 升級時）       | 更新 severity 和 message（數值變化時必須更新） |
| **解決條件** | 設備恢復連線                             | 數值恢復正常                                   |
| **錯誤追蹤** | 使用 `error_tracking` 表                 | 不使用錯誤追蹤                                 |
| **警報數量** | 同一設備同一類型只有 1 個                | 同一位置可能有多個（不同參數）                 |

### 流程對比

**設備連線警報**：

```
設備連接失敗 → errorTracker.recordError() → error_count++
→ error_count >= 5? → 檢查忽視狀態 → createAlert()
→ 檢查現有警報（簡單匹配） → 創建/更新警報 → WebSocket 推送
```

**閾值警報**：

```
環境監控任務 → 讀取感測器讀數 → 查詢規則（緩存）
→ 評估參數 → 超過閾值? → 檢查忽視狀態（參數匹配）
→ createAlert() → 檢查現有警報（參數匹配）
→ 創建/更新警報 → WebSocket 推送
```

## API 端點

### 查詢警報

- **`GET /api/alerts`** - 取得警報列表（公開）

  - 支援過濾：`source`, `source_id`, `alert_type`, `severity`, `status`, `start_date`, `end_date`
  - 支援增量查詢：`updated_after`（只獲取更新時間在此之後的警報）
  - 支援分頁：`limit`, `offset`
  - 支援排序：`orderBy`, `order`

- **`GET /api/alerts/unresolved/count`** - 取得未解決警報數量（公開）

  - 支援過濾：`source`, `source_id`, `alert_type`, `severity`

- **`GET /api/alerts/:id/history`** - 取得警報歷史記錄（公開）

### 管理警報（需要認證，管理員）

- **`PUT /api/alerts/:id/unresolve`** - 標記警報為未解決（重新激活）

  - 將已解決的警報重新標記為 active

- **`POST /api/alerts/:deviceId/:alertType/ignore`** - 忽視警報

  - 支援 `source` 參數（可選，默認為 `device`）

- **`POST /api/alerts/:deviceId/:alertType/unignore`** - 取消忽視警報
  - 支援 `source` 參數（可選，默認為 `device`）

## WebSocket 事件

### 事件類型

1. **`alert:new`** - 新警報創建（首次創建 active 警報）
2. **`alert:updated`** - 警報更新（數值更新、severity 升級、狀態變更）
3. **`alert:count`** - 未解決警報數量更新（防抖處理，避免頻繁推送）

**事件數據結構**：

```json
{
  "alert": {
    /* 完整的警報對象 */
  },
  "oldStatus": "active",
  "newStatus": "active",
  "timestamp": "2025-01-08T10:15:00Z"
}
```

## 警報歷史記錄

### 歷史記錄功能

系統自動記錄所有警報狀態變更歷史到 `alert_history` 表。

**記錄時機**：

- ✅ 手動更新狀態（通過 `updateAlertStatus` API）
- ✅ 自動解決警報（設備恢復連線、數值恢復正常）
- ✅ 手動重新激活（`unresolve` API）
- ✅ 忽視/取消忽視警報
- ❌ 警報創建時（沒有狀態變更，不記錄）

**記錄內容**：

- `alert_id` - 警報 ID
- `old_status` - 舊狀態
- `new_status` - 新狀態
- `changed_by` - 變更者用戶 ID（系統自動解決時為 `null`）
- `changed_at` - 變更時間
- `reason` - 變更原因（可選）

**查詢 API**：`GET /api/alerts/:id/history`

### 實際使用情況

歷史記錄在以下場景會被自動創建：

1. **設備連線警報自動解決**：

   - 設備恢復連線時，`errorTracker.clearError()` → `resolveActiveAlerts()` → `updateAlertStatus()`
   - 記錄：`active` → `resolved`，`changed_by = null`，`reason = "系統檢測到問題已恢復"`

2. **閾值警報自動解決**：

   - 感測器數值恢復正常時，`environmentMonitor` → `updateAlertStatus()`
   - 記錄：`active` → `resolved`，`changed_by = null`，`reason = "數值已恢復正常"`

3. **手動管理操作**：
   - 管理員忽視/取消忽視、重新激活警報時
   - 記錄：包含 `changed_by`（管理員用戶 ID）和可選的 `reason`

### 使用場景

- 追蹤警報狀態變更歷史
- 審計和合規要求
- 問題分析和調試
- 查看警報的完整生命週期

## 警報自動清理

### 清理服務 (`alertCleanupService.js`)

**自動備份和清理**：

- **資料庫保留**：已解決的警報在資料庫中保留 30 天（前端可追溯時間）
- **備份保留**：備份檔案保留 365 天
- **執行頻率**：每天執行一次（定時任務）

**清理流程**：

1. 查詢超過 30 天的已解決警報
2. 備份到 JSON 檔案（`backups/alerts/alerts_archive_YYYYMMDD.json`）
3. 從資料庫刪除已備份的警報
4. 刪除超過 1 年的舊備份檔案

**啟動方式**：系統啟動時自動啟動（`server.js` 中調用 `startCleanupScheduler()`）

## 性能優化

### 已實施的優化

1. **規則緩存機制** - 減少資料庫查詢約 20-30%
2. **參數提取優化** - 統一的輔助函數，避免重複提取
3. **日誌輸出優化** - 減少日誌輸出量約 70-80%

6. **一次性查詢** - Active 警報一次性查詢所有位置
7. **增量查詢支持** - `updated_after` 參數支持前端增量輪詢
8. **防抖處理** - 未解決警報數量更新使用防抖，避免頻繁推送

| ---------------------- | ------------ | ---------------- |
| 資料庫查詢（每次監控） | 5 次規則查詢 | 0 次（使用緩存） |
| 日誌輸出量             | 100%         | 20-30%           |
| 系統負載               | 基準         | 降低 20-30%      |
