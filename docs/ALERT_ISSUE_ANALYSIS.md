# 警報合併問題分析報告

## 問題描述

用戶反映：在附圖中看到 1F（工地管理）和遠岫（展廳）同時出現 PM2.5 的警報，但在警示紀錄中只看到一個。

## 診斷結果

### 1. 資料庫結構檢查

- ✅ 兩個地點有獨立的 `location_systems` 記錄：

  - System ID: 9, Location: 展廳 (遠岫), Device ID: 3
  - System ID: 10, Location: 工地管理 (1F), Device ID: 3

- ✅ 兩個地點共用同一個感測器設備（Device ID: 3）

### 2. 感測器讀數檢查

- **展廳**：

  - 最新讀數時間：2026-01-16 09:02:10
  - PM2.5 值：16 µg/m³（低於閾值 25）

- **工地管理**：
  - 最新讀數時間：2026-01-16 15:49:24
  - PM2.5 值：26 µg/m³（超過閾值 25）

### 3. 警報記錄檢查

- ✅ 目前只有一個活躍警報：

  - Alert ID: 130
  - Source ID: 10（工地管理）
  - Status: active
  - Message: "工地管理 的 PM2.5 超過 25µg/m³，當前值：26µg/m³（注意）"

- ✅ 展廳的警報都是已解決的（resolved）

### 4. 警報查詢邏輯檢查

- ✅ GROUP BY 邏輯正確：

  ```sql
  GROUP BY a.source, a.source_id, a.alert_type, a.status
  ```

  這個 GROUP BY 會將相同 `source_id` 的警報合併，但不會合併不同 `source_id` 的警報。

## 問題分析

### 可能的原因

1. **展廳的讀數沒有更新**：

   - 展廳的最新讀數時間是 09:02:10，而工地管理的最新讀數時間是 15:49:24
   - 如果展廳的讀數很久沒有更新，環境監控服務可能無法檢查到超過閾值的情況

2. **前端顯示的是讀數狀態，而不是警報記錄**：

   - 前端可能根據感測器讀數是否超過閾值來顯示警告狀態
   - 但實際上只有當環境監控服務檢查並創建警報後，才會在警示紀錄中顯示

3. **環境監控服務的檢查邏輯**：
   - 環境監控服務會從 `sensor_readings` 表中讀取每個地點的最新讀數
   - 如果某個地點的讀數很久沒有更新，就不會產生新的警報

## 解決方案

### 方案 1：確保所有地點的讀數都及時更新

如果兩個地點共用同一個感測器設備，需要確保：

1. 前端在讀取感測器資料時，為所有使用該設備的地點都儲存讀數
2. 或者後端在讀取感測器資料時，為所有使用該設備的地點都儲存讀數

### 方案 2：改進環境監控服務的邏輯

如果兩個地點共用同一個感測器設備，可以：

1. 從感測器讀取一次資料
2. 為所有使用該設備的地點都儲存讀數
3. 為所有使用該設備的地點都檢查閾值

### 方案 3：檢查前端顯示邏輯

確認前端是否正確區分：

1. 感測器讀數的狀態（是否超過閾值）
2. 實際的警報記錄（是否在警示紀錄中）

## 建議

1. **檢查感測器讀數的儲存邏輯**：

   - 確認當讀取感測器資料時，是否為所有使用該設備的地點都儲存讀數

2. **檢查環境監控服務**：

   - 確認環境監控服務是否正確處理所有地點的讀數

3. **檢查前端顯示邏輯**：
   - 確認前端是否正確顯示警報狀態
